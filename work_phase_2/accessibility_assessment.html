Accessibility Assessment

Text Readability

Potential Issues

The website uses very small font sizes with tight line spacing, and colour contrast between text and background is often too low (for example, light grey on white). In many places, colour is the only means of conveying information, such as using red for “spicy” and green for “healthy.” This makes it difficult for users with visual impairments and also reduces clarity for everyone in low-light environments.

Expectations of Users

Users expect text to be adjustable in size and to meet contrast standards. Busy parents want to be able to quickly identify nutritional or timing labels even when glancing at a screen in a dimly lit kitchen. Visually impaired users expect a one-tap option to switch to a high-contrast theme with enlarged fonts.

Improvement Suggestions

Body text should be at least 16px with a line height of 1.5 and paragraph spacing double the text height. Text must be scalable up to 200% without overlapping or loss of functionality (WCAG 1.4.4 Resize Text). Normal text should have a contrast ratio of at least 4.5:1, while large text (18pt bold or 24pt regular) should have at least 3:1 (WCAG 1.4.3 Contrast Minimum, 1.4.11 Non-text Contrast). Do not rely on colour alone: add icons or text labels, such as “Spice Level 🌶️ x2” (WCAG 1.4.1 Use of Colour). Provide a high-contrast theme and one-tap large-text mode that remembers user preferences.

Non-Text Content

Potential Issues

Images of recipe steps and finished dishes often lack descriptive alt text, or are labelled only as “image.” Videos and animations usually do not include subtitles or audio/text descriptions of key actions. Nutritional information is often presented only as static images, which screen readers cannot interpret.

Expectations of Users

Users want step-by-step visuals with meaningful text. Busy parents need clear pictures with short captions. Visually impaired users depend on alt text and screen readers to understand actions such as “onions turning translucent.”

Improvement Suggestions

All meaningful images must have descriptive alt text explaining actions, states, and outcomes, while decorative images should use empty alt attributes (WCAG 1.1.1 Non-text Content). Videos must include subtitles, and any visual-only information should have audio or text descriptions (WCAG 1.2 Captions and Audio Description). Nutritional data and ingredient lists should be coded as semantic HTML tables (WCAG 1.3.1 Info and Relationships), and large-print PDF versions should be made available.

Information Structure and Understandability

Potential Issues

Some pages lack <h1> headings, or heading levels are skipped, breaking the logical order for screen readers. Recipe instructions are often written in long paragraphs instead of short, numbered steps, and they lack labels such as “Prep,” “Cook,” or “Note.” For multilingual content, the absence of language attributes (lang) causes incorrect screen reader pronunciation.

Expectations of Users

Busy professionals expect clear workflows of no more than six steps, with the ability to do tasks in parallel. Visually impaired users need short, numbered instructions with clear labels so that the screen reader reads them in a logical order.

Improvement Suggestions

Use semantic structure with one <h1> per page and a proper hierarchy of h2 and h3 (WCAG 1.3.1 Info and Relationships, 2.4.6 Headings and Labels). Provide a “skip to content” link for efficiency (WCAG 2.4.1 Bypass Blocks). Break instructions into no more than two sentences per step, prefixed with labels such as [Prep], [Cook], or [Note] (WCAG 3.1.5 Reading Level). Use bullet points or subsections for parallel actions. Add correct lang attributes for multilingual text so that screen readers pronounce it accurately (WCAG 3.1.2 Language of Parts).

Keyboard Navigation and Focus

Potential Issues

Interactive elements such as filters, workflow panels, and pop-ups often cannot be used without a mouse, and modals cannot be closed with the Esc key. Focus indicators are weak or become hidden behind sticky headers or overlays, making it hard to track navigation. The tab sequence often does not follow the visual layout, confusing screen reader users.

Expectations of Users

All users expect to complete tasks using only the keyboard, including opening filters, setting options, reviewing results, and closing dialogs. Visually impaired users in particular need strong, visible focus indicators and a predictable tab order.

Improvement Suggestions

Ensure the entire site is keyboard operable, with no keyboard traps (WCAG 2.1.1 Keyboard, 2.1.2 No Keyboard Trap). All modals should close with Esc. Focus indicators must be visible and unobstructed, with at least a 3px high-contrast outline (WCAG 2.4.7 Focus Visible, 2.4.11 Focus Appearance). The DOM order should match the visual order, and tabindex should be managed carefully. Add “skip to filter” and “skip to results” links (WCAG 2.4.1 Bypass Blocks).

Forms and Interaction

Potential Issues

Form controls such as checkboxes, toggles, or dropdowns often lack visible labels or accessible aria-labels. Error messages are shown only with colour and are not linked to input fields. Login and comment forms sometimes require solving CAPTCHAs or memory tasks, creating unnecessary cognitive load.

Expectations of Users

Busy parents and professionals want fast, forgiving forms. Visually impaired users expect labels that screen readers can read, error messages that point to the correct field, and accessible authentication methods.

Improvement Suggestions

Every input must have a label, either visible or via aria-labelledby (WCAG 3.3.2 Labels or Instructions). Required fields should be indicated with text, not colour alone (WCAG 1.4.1 Use of Colour). Error messages must be linked to fields using aria-describedby and provide clear instructions for correction (WCAG 3.3.1 Error Identification). Replace puzzle-based authentication with accessible alternatives such as email magic links, biometrics, or Passkeys (WCAG 3.3.7 Accessible Authentication, 3.3.8 Redundant Entry). Provide options to show or hide passwords.

Touch Targets and Drag Alternatives

Potential Issues

On mobile devices, buttons are often too small and too close together, leading to frequent mis-taps. Some interactions, such as reordering steps, rely only on drag-and-drop with no alternative method. Cooking timers cannot be paused, stopped, or reset, and they lack auditory or textual status feedback.

Expectations of Users

Busy users operating the site one-handed need larger, easier-to-hit targets. Visually impaired users need non-drag alternatives and feedback through sound or text to understand timer status.

Improvement Suggestions

Touch targets should be at least 24*24px with 8-12px spacing between elements (WCAG 2.5.8 Target Size). All drag-and-drop interactions must have button alternatives such as “move up,” “move down,” or “move to position N” (WCAG 2.5.7 Dragging Movements). Timers should include pause, stop, and reset functions, with ARIA live regions announcing status updates (WCAG 2.2.1 Timing Adjustable, 4.1.3 Status Messages).
